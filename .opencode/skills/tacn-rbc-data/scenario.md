# 场景序列 — 一条需求生成一组模拟器 XML

一个场景通常不是一条报文，而是有先后顺序的一组报文。本文件把常见场景固定成
「报文序列 + 包组成 + 必问项」，一次生成整组模拟器 `DataTable` XML。

单条报文的字段规则、取值写法、XML 格式仍以 `sim-xml.md` 为准；本文件只定义
场景怎么拆成序列、每组要问什么、文件和交付怎么排。

## 规则

1. **只出模拟器 XML，只含 RBC→车**。场景里需要车→地报文时，模拟器回放不了，改用
   `generate.md` 出 hex；两者都要时在 `intent.target` 写 `both`。
2. **一份 values JSON 就是一个场景**：每个报文一个顶层分组，按空口顺序排列；每个分组
   带自己的 `intent` + `provenance`（`references/gate.md`）。
3. **文件名按投递顺序编号**：分组里用 `"file": "01_M24_CTCS80.xml"` 这类有序名。默认的
   `dataTableM<n>.xml` 只对同类型单条能自动加载；同场景里同类型有多条（例如两个 M24）
   必须改名，否则会生成 `_2`，且这些文件不会按名字自动加载，需在模拟器里手动选。
4. **时序不进 XML**：像“10 s 内发第二条”“ATP 进入已编组状态后再发”这类要求写在交付说明
   里，由操作员执行；不要试图用字段表达。
5. **包组成以 `protocol.md` 为准，可用范围以 `gen_rbc_sim_xml.py --list` 为准**。两边都满足
   才能生成；模拟器分派表之外的包不要尝试。
6. **不替用户编业务值**：场景只决定“发哪几条、每条带哪些包”，字段值仍按 `references/gate.md`
   的确认单逐项收齐。能算出来的（如按距离换算的 `D_MAMODE`）可以算，但要在确认单里写清算法和来源。

## 输出形态

```
scenario.json          # 一份 values JSON，N 个分组
out/01_M24_CTCS80.xml
out/02_M24_CTCS81.xml
out/03_M3.xml
```

一条命令生成全部：`gen_rbc_sim_xml.py --values scenario.json -o out/`。生成器按 JSON 里的
分组顺序处理，任何一组过不了门禁或校验就整批不写。交付说明里给一张序列表：

| 序 | 文件 | 消息 | 包 | 字节 / bit | 投递时机 |
|---|---|---|---|---|---|

## 场景 1 进入虚拟编组模式

| 序 | 报文 | 包组成 | 说明 |
|---|---|---|---|
| 1 | M24 | P44 → CTCS-80（编组命令） | `M_ACK=1`；带 `GROUP_ID`、`N_TRAINNUM`、按编组顺序的 `Group_NID_ENGINE(k)`、`NID_ENGINE_PRE`、`M_IP_PRE` |
| 2 | M24 | P44 → CTCS-81（编组状态） | `M_ACK=1`；只有 `GROUP_ID`；与第 1 条间隔 **≤10 s** |
| 3 | M3 | P5、P15、P21、P27（不具备车车通信时加 P44 → CTCS-150） | ATP 进入已编组状态后发；`P15` 必选 |

必问（缺一项就停下来问）：

- 本车与前车的 **NID_ENGINE（24 位设备号）**。用户给的是**车次号**时必须追问 —— 车次号不是
  `NID_ENGINE`，不要自行换算或把车次号直接填进去。
- `GROUP_ID`（编组标识，32 位；`0xFFFFFFFF` 表示未编组）。
- `N_TRAINNUM` 与编组顺序（`Group_NID_ENGINE` 行数必须等于 `N_TRAINNUM`）。
- 前车双网 IP（`M_IP_PRE`，八段点分十进制）。
- 是否具备车车通信 —— 决定第 3 条 M3 带不带 `CTCS-150`。
- MA 的 `P15`/`P21`/`P27`/`P5` 取值（可直接问，也可从已有报文反解导出）。
- 输出目录、文件名前缀、是否覆盖。

长度锚点：`M24 + CTCS-80（N_TRAINNUM=2）` 应为 294 bit / 37 字节（外层 219、内层 196）；
`M24 + CTCS-81` 为 154 bit / 20 字节（外层 79、内层 56）；
`M3 + P5+P15+P21+P27 + CTCS-150` 应为 653 bit / 82 字节。不带 `CTCS-150` 的 M3 没有基线，
按生成器回填的实际值报告。

对话示例：

```
用户：帮我生成一份进入虚拟编组模式的报文
→ 贴确认单（3 条序列）+ 问：本车/前车 NID_ENGINE、GROUP_ID、N_TRAINNUM 与编组顺序、
  前车 IP、有没有车车通信、MA 取值、输出目录
用户：本车 90，前车 91，没有车车通信……
→ 更新确认单，逐项标来源，确认后生成 3 个文件
```

## 场景 2 CN 等级转入 C0

单条报文：`M24 + P41`。

| 字段 | 取值 |
|---|---|
| `M_LEVELTR` | 1（C0/C2） |
| `NID_STM` | 1（C0）；`M_LEVELTR=1` 时必带 |
| `D_LEVELTR` | 需求里的距离；`32767` = 立即转换 |
| `L_ACKLEVELTR` | 等级转换确认区段长度，默认 450 |

必问：多少米后转换（`D_LEVELTR`）、等级转换确认区段长度（`L_ACKLEVELTR`，不给就用 450 并标
“协议默认”）、`Q_SCALE`（默认 1 m）。

长度参考：`N_ITER=0` 时 P41 为 71 bit，整条 M24 为 19 字节。
P41 的 `M_LEVELTR`/`NID_STM`/`L_ACKLEVELTR` 在主段和迭代段同名，生成器可能提示
“该帧声明了 2 次”；`N_ITER=0` 时按裸名写即可，确需区分时写 `M_LEVELTR#1`。

对话示例：

```
用户：帮我生成一份 600 m 后转入 C0 等级的报文
→ 问：等级转换确认区段长度
用户：200 m
→ D_LEVELTR=600、L_ACKLEVELTR=200，M_LEVELTR=1、NID_STM=1，生成 1 个文件
```

## 场景 3 C0 等级转入 CN

两条报文，按顺序：

| 序 | 报文 | 包组成 | 说明 |
|---|---|---|---|
| 1 | M24 | P41 | `M_LEVELTR=4`（CN）。**不带 `NID_STM`** —— 该字段只在 `M_LEVELTR=1` 时存在，照抄场景 2 会被生成器拒绝 |
| 2 | M3 | P15、P21、P27 | 等级转换预告收到后再发行车许可 |

必问：`D_LEVELTR`、`L_ACKLEVELTR`、MA 的 `P15`/`P21`/`P27` 取值、输出目录与文件名。

长度参考：`N_ITER=0` 时 P41 为 63 bit（不带 `NID_STM`），整条 M24 为 18 字节。

## 场景 4 自由场景（一条 M3 组合多个包）

用户用自然语言描述一段线路，把它拆成一条 M3 的信息包组合。以示例需求为模板：

> 先以完全模式运行，2 km 处有 500 m 临时限速 60 km/h，3 km 处有 800 m 分相区，
> 出分相区后转入引导模式，限速 40 km/h、引导区段 500 m。

| 需求片段 | 映射 |
|---|---|
| 完全模式运行 | 背景说明，不进报文（模式由 ATP 状态决定） |
| 2 km 处 500 m 限速 60 km/h | `P65`：`D_TSR=2000`、`L_TSR=500`、`V_TSR=60`、`NID_TSR` 取 127~254 的 RBC 自定值、`Q_FRONT` 按需求 |
| 3 km 处 800 m 分相区 | `P68`：`Q_TRACKINIT=0`、`D_TRACKCOND=3000`、`L_TRACKCOND=800`、`M_TRACKCOND=1001`（无电区关主断） |
| 出分相区后转引导，限速 40、区段 500 m | `P80`：`D_MAMODE=3800`、`L_MAMODE=500`、`V_MAMODE=40`、`M_MAMODE=0`（引导 CO）、`L_ACKMAMODE` 按需求或默认 400 |
| 行车许可终点 | `P15`（M3 必选） |

自由场景的规则：

1. 包只能从模拟器分派表里选（M3：P3、P5、P15、P21、P27、P65、P66、P68、P80、CTCS-132、CTCS-150）。
2. 需求里没有对应包的内容（“完全模式”“司机确认”等）不进报文，写进交付说明。
3. 距离、长度按 `Q_SCALE` 换算（默认 1 m），确认单里写清单位与换算过程。
4. 分相区固定用 `P68 M_TRACKCOND=1001`；其它线路条件按 §5.12 的取值表（禁停隧道/桥梁、
   无线盲区、防汛区段等），需求里没有的不要加。
5. 多个限速、多个线路条件按 `N_ITER` 展开；`NID_TSR` 必须互异（规则 1-9）。

必问：EOA 位置、`P15` 的区段划分、要不要带 `P21`/`P27`/`P5`、`Q_SCALE`、各距离的起点
（LRBG 还是上一个区段末端）、输出目录与文件名。

## 生成流程

1. **定序列** —— 按上面的场景表定“发哪几条、每条带哪些包、顺序和间隔”；自由场景先做需求 → 包映射，
   映射拿不准就问，不要猜。
2. **收齐取值** —— 按 `references/gate.md` 的确认单逐项确认；场景表里的“必问”是补充项，不是替代项。
3. **写一份 values JSON** —— 每个报文一个分组，键名建议 `s1_m24_c80` 这种带序号的写法；
   每组 `intent.target="sim-xml"`、`intent.packets` 与实际包顺序一致、`provenance` 逐段标来源；
   用 `file` 写有序文件名。
4. **生成** —— `python <skill-dir>/scripts/gen_rbc_sim_xml.py --values scenario.json -o out/`；
   含占位值时显式加 `--allow-placeholder`。
5. **核对与交付** —— 逐文件核对 `L_MESSAGE`/`L_PACKET` 与组成；给出序列表、每个文件的长度、
   投递顺序与间隔、审计行与占位清单；说明“没有在模拟器里实际加载/发送”。

## 失败处理

| 报错 / 情况 | 处理 |
|---|---|
| `RBC 模拟器只支持 RBC→车消息` | 场景里混入了车→地报文；那几条走 `generate.md` 出 hex |
| `RBC 模拟器不支持 P##` / `P44/CTCS-…` | 该包不在分派表；换包、换场景，不要靠 XML 造包 |
| `输出文件名重复` | 两个分组用了同一个 `file`；按序号区分 |
| `当前限定词下该字段不进报文` | 典型是 `M_LEVELTR≠1` 却给了 `NID_STM`；删掉该字段 |
| `N_TRAINNUM` 与 `Group_NID_ENGINE` 行数不符 | 编组顺序没给全；按 `N_TRAINNUM` 补齐 |
| 场景要求的包不属于该消息（如 M24 带 `P15`） | 报文本身不成立；改场景（用 M3）或去掉该包 |
| `缺少必选信息包` | M3 少了 `P15`；补上再生成 |

## 限制

- 模拟器只能回放 RBC→车；场景里车→地的一侧要另出 hex。
- 一组场景的报文是一次性生成的：任何一条过不了门禁或校验，整批都不写文件。
- 时序、间隔、加载顺序都要人工在模拟器里执行，XML 不表达这些。
- 仓库里没有 RBC 模拟器可执行文件；生成成功只说明文件符合本文档与 `sim-xml.md` 的格式，
  不证明 ATP 侧行为。
